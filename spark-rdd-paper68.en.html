Resilient Distributed Datasets (Spark RDD)

Zaharia, Chowdhury, Das, Dave, Franklin, Shenker, Stoica et al. · UC Berkeley AMPLab · NSDI 2012

中文 →

What did this paper do?

In 2012 a group at UC Berkeley proposed RDDs (Resilient Distributed Datasets) and built Spark on top of them — the engine almost every company now reaches for when the data is too big for one machine. Before it, that job went to Hadoop MapReduce. RDDs made the same work an order of magnitude faster in a lot of cases, and made "type one line, a hundred machines answer in seconds" an ordinary thing to do.

Start with something odd

When you gang a hundred machines together to crunch data, the thing to fear is not slowness — it is a machine dying halfway through. Run a hundred of them for a few hours and one or two will drop out, taking their slice of data and their half-finished work with them. The old answer was blunt and effective: after every step, write the intermediate results all the way out to disk, in triplicate. When a machine dies, fetch the results back and carry on.

The trouble shows up in work that has to go over the same data again and again — training a model, ranking web pages, dozens of passes over one batch. The old way writes to disk and reads back on every single pass. The data never changed, yet it got hauled in and out dozens of times. Nearly all the time went into hauling, not into computing.

The idea

So leave the data in memory and stop hauling it — except now, when a machine dies, what was in its memory is genuinely gone. Which puts the old question back: no triplicate copies, no disk, so what happens when something breaks?

The RDD answer is lovely: don't store the results, store the method.

Picture a kitchen with twenty trays of prepped ingredients. Afraid of losing them, most people would photograph every tray and stash two spare copies in the walk-in — bulky and slow. RDDs say: no need. Here is a recipe card — this tray came from that tray via this one step, that tray came from an earlier one, and the chain runs all the way back to the original sack of produce. Lose a tray and you remake that one tray from the card; every other tray is untouched. The card is a few lines of text, so keeping it costs essentially nothing. The paper calls this card the dataset's lineage.

Why the recipe card stays short

Because of one piece of self-restraint: only whole-tray steps are allowed — chop everything on this tray, throw out everything that isn't spicy, pair these two trays up by name. What is not allowed is "add half a spoon of salt to potato number 37."

That restriction is the whole trick. Allow the fiddly per-item edits and what you must record is not a few lines but millions of ledger entries — at which point you may as well have stored the results. Record only whole-tray moves and the card stays short enough to hand a copy to every machine in the building. And since big-data work is overwhelmingly "do the same thing to all of it," giving up the fiddly edits barely hurts.

One more rule: once a tray is made it may never be altered — changing it means making a new tray. Precisely because nothing can be altered underneath you, a tray remade from the card is identical to the one you lost. That is what makes remaking count as recovery.

What it bought

Data can now sit in memory and be reused with confidence, so repetitive work got more than ten times faster. A dead machine no longer restarts the whole job — only the lost pieces get remade, and they can be remade on many machines at once. Better still, it changed how people relate to data: a question over a few terabytes used to mean a coffee break; now you can ask one after another like using a calculator, seconds per answer.

One honest cost: this approach is hungry for memory, and it only works for whole-batch jobs — if what you want is to update one record at a time as news arrives, RDDs cannot help you; that is a different kind of system's job.

One line to remember

Spread the data across cluster memory in blocks, allow only whole-dataset transformations, and never let a block be altered once made. Then fault tolerance needs no triplicate copies — just a record of how each block was produced, so a lost block can be rebuilt from its recipe. That is what lets data stay in memory and be reused: iterative jobs get an order of magnitude faster, and a terabyte can answer a question in seconds.

In one sentence

RDDs are read-only, partitioned collections that can only be created by coarse-grained transformations over other RDDs or stable storage. Because writes are restricted to "apply one transformation to the whole dataset," the system only has to log the graph of those transformations — the lineage — and can recompute lost partitions after a node failure instead of replicating data across machines or logging fine-grained updates the way earlier in-memory systems had to. That made it safe, for the first time, to keep working data resident in cluster memory and reuse it, and it made iterative machine learning, graph computation, and interactive querying an order of magnitude faster than Hadoop MapReduce.

Glossary

  • Cluster / node: tens to thousands of ordinary machines wired together and used as one big machine; each machine is a node. At that scale "some machine is always broken" is the normal state, not an accident.
  • MapReduce: the batch model from Google, implemented by Hadoop — split work into map (do the same thing to every record) and reduce (aggregate everything sharing a key), with intermediate results written to a distributed file system.
  • HDFS / distributed file system: storage that chops a large file into blocks spread over many machines' disks, several copies of each block. Every access goes through disk and network, so it is far slower than memory.
  • Partition: one slice of a large dataset. It is the unit of parallelism and of failure recovery — each machine holds some partitions.
  • Replication: keeping the same data on several machines so a loss is survivable. Safe, but it multiplies storage and pushes data across the network.
  • Checkpoint: deliberately writing the current state out to reliable storage (such as HDFS), so that after a failure you resume from there instead of from the beginning.
  • Iterative algorithm: one that must sweep the same data many times before converging — logistic regression, k-means clustering, PageRank.
  • Logistic regression / k-means: two classic machine-learning algorithms, one learning a yes/no decision boundary, the other sorting points into k groups. Both make dozens of passes over one dataset.
  • Shuffle: regrouping one stage's output by key, which moves records across every machine before the next stage can start. It is the most expensive move in distributed computing.
  • DAG (directed acyclic graph): a graph of one-way arrows with no cycles; here it records "what was computed from what."
  • Distributed shared memory (DSM): an abstraction letting machines in a cluster read and write a global memory as if it were local, with fine-grained access anywhere — flexible, and hard to make fault-tolerant precisely because it is so flexible.
  • Lazy evaluation: writing down a chain of transformations computes nothing; the work is planned and run only when a result is actually demanded.

Coordinates

The authors are Matei Zaharia, Mosharaf Chowdhury, Tathagata Das, Ankur Dave, Michael Franklin, Scott Shenker, Ion Stoica and colleagues at UC Berkeley's AMPLab; the paper appeared at NSDI 2012 and won Best Paper. It follows the cluster batch-processing lineage of MapReduce (2004) and Dryad, plus the wave of purpose-built systems — Pregel, HaLoop, iterative MapReduce — each solving one workload. Downstream it grew into the whole of Apache Spark: Spark SQL, MLlib, GraphX and Structured Streaming all sit on this abstraction.

The problem

MapReduce made "run a job on a thousand unreliable machines" tractable, but it carries one hard design decision: stages hand off through stable storage. Each round's output is written to HDFS (replicated three ways) and the next round reads it back. For "sweep the data once, emit a report," that is fine.

Two increasingly important workloads choke on it:

  • Iterative algorithms. Logistic regression, k-means and PageRank run dozens of rounds over the same data. MapReduce re-reads that data from disk every round and writes the intermediate state back out — the data never changed, yet it is hauled in and out dozens of times, and the I/O plus serialization cost swamps the actual computation.
  • Interactive data mining. An analyst wants to ask a dozen questions of one dataset. Each question is a fresh job that rescans disk, so each answer takes tens of minutes — which makes exploratory analysis impossible in practice.

So why not simply build a cluster-memory abstraction? Because the existing ones — distributed shared memory and in-memory key-value stores such as Piccolo and RAMCloud — all permit fine-grained updates: any process may write any cell. Flexible, but it leaves exactly two routes to fault tolerance: replicate the data across machines, or log every update and ship the log across machines. Both push large volumes over the network, and for data-intensive workloads that cost can eat the entire benefit of being in memory. The hard part was never "put the data in memory"; it was "make it cheap to survive failure once it is there."

Core idea and method

1. Restrict writes to coarse-grained, and recomputation becomes viable

The whole answer hides in the definition: an RDD is a read-only collection of records split into partitions, and it can only be created by applying one deterministic transformation to another RDD (or to data in stable storage) — map, filter, join, groupByKey and friends, all of which act on the entire dataset. You cannot reach in and edit one record.

That looks like a loss of power. It is a precise trade: since every RDD can only have come from some (parent RDD, transformation) pair, recording that provenance is the same as holding the complete recipe for rebuilding it. The chain of provenance is the lineage — a DAG of "who was computed from whom, by which transformation."

The fault-tolerance arithmetic then reads: store nothing extra in the normal case (lineage is tens of bytes of metadata, not data), and on failure recompute only the lost partitions, leaving every other partition alone and rolling nothing back. Several lost partitions can be rebuilt in parallel on different nodes, so recovery speed scales with the cluster.

One premise is easy to skip past and decides everything: RDDs are immutable and transformations are deterministic. Because no parent can be mutated behind your back and the transformation is a pure function, a recomputed partition is byte-for-byte what was lost — which is why recomputation is recovery rather than a different answer. Mutable state with fine-grained updates cannot offer that, because it can neither record nor replay the path that produced a given value.

2. Narrow versus wide dependencies: one distinction that explains both execution and recovery

"Just recompute it" is not enough on its own, because the cost of recomputing varies enormously. The paper draws a line that is still the core of Spark's mental model:

  • Narrow dependency: each partition of the parent is used by at most one child partition (map, filter, a join on already co-partitioned inputs). Parent and child line up one to one.
  • Wide dependency: a child partition draws on many or all partitions of the parent (groupByKey, a join that is not co-partitioned), which requires an all-to-all shuffle across machines.

Drawing that line answers two questions at once. For execution, a run of narrow dependencies can be pipelined on a single machine — take a record, map it, filter it, never materialize, never touch the network. The scheduler therefore cuts the DAG into "stages" exactly at wide dependencies: inside a stage everything is narrow and pipelines freely; between stages there is one shuffle. For recovery, a narrow dependency means rebuilding a lost partition needs only the few matching parent partitions — cheap. A wide dependency means losing one partition may force recomputing all partitions of an ancestor RDD — expensive enough to be worth checkpointing against.

3. The programming interface: lazy transformations, eager actions

There are only two kinds of operation. Transformations — map, filter, join — are lazy: writing one down merely adds a node to the lineage graph and computes nothing. Actions — count, collect, save — are what trigger execution. Laziness pays off concretely: the system receives the whole graph rather than a stream of isolated commands, so it can fuse runs of narrow dependencies into pipelines and place tasks on the nodes that already hold the data.

A user can also call persist() (cache) on an RDD to say "I will reuse this; keep it in memory," choosing a storage level: deserialized Java objects in memory (fastest), serialized bytes in memory (more compact), or spilled to disk. When memory runs short, partitions are evicted LRU at partition granularity — evicting can never produce a wrong answer, only a recomputation from lineage next time. The paper's interactive example is written exactly this way: filter the error lines out of a log, persist them, then run dozens of queries against that in-memory dataset.

4. When lineage is not enough: checkpointing

Lineage has a limit. When the chain is both long and full of wide dependencies — say dozens of PageRank iterations, each with a shuffle — a single node failure can trigger something close to a full recomputation, and recovery time becomes unacceptable. That is when the old method earns its place: checkpoint some generation of the RDD to HDFS and truncate the lineage there.

Worth noting how much easier RDDs make checkpointing: because RDDs are immutable, a checkpoint can be written lazily in the background — there is no need to pause for a consistent snapshot and no risk of the data changing mid-write. The paper leaves when to checkpoint automatically as future work and exposes it as an explicit user call.

Key results

The Spark implementation in the paper is about 14,000 lines of Scala running on Mesos, with a modified Scala interpreter for interactive use. The main experiments, mostly on 100 Amazon EC2 machines:

  • Iterative machine learning. Logistic regression and k-means over 100 GB ran up to roughly 20× faster than Hadoop. The source of the gap is laid out plainly: the first iteration is comparable because both read HDFS; from the second iteration on, Spark works from the in-memory RDD while Hadoop re-reads the disk, paying serialization and deserialization every round.
  • Interactive queries. With 1 TB cached in memory, query latency landed at 5–7 seconds; the same queries against disk took on the order of a hundred seconds. That is the boundary between "wait half a minute" and "go get coffee."
  • Failure recovery. Killing a node mid-way through k-means slowed only the iteration during which it died — the lost partitions were rebuilt in parallel across nodes — and subsequent iterations returned to normal speed, rather than the job restarting.
  • Graceful degradation under memory pressure. Given only part of the working set's worth of cache, performance declined smoothly instead of collapsing; partitions that did not fit fell back to recomputation or disk.
  • Expressiveness. The authors reimplemented MapReduce and Pregel's model (as Bagel, about 200 lines of Scala) on top of RDDs, showing the abstraction subsumes a batch of earlier special-purpose systems — not one more framework, but a general substrate wide enough to hold them. Graph algorithms like PageRank gain further by controlled partitioning: co-partitioning the two tables being joined turns a wide dependency into a narrow one and removes a shuffle.

Why it mattered

Three layers. Directly: Apache Spark became MapReduce's de-facto successor and the workhorse of the last decade of large-scale data processing, with Spark SQL, MLlib, GraphX and Structured Streaming all built as libraries over RDDs — which is precisely the "one general abstraction subsuming many specialized systems" claim, cashed in.

As an idea: it established "recompute from lineage instead of replicating data" as a legitimate route to distributed fault tolerance. That reaches far beyond Spark — any system whose inputs are immutable and whose computation is deterministic can use it, which is why the same reasoning shows up in re-runnable data pipelines, event sourcing, and the recompute semantics of modern orchestration and data-build tooling.

As method: it demonstrates the most valuable move in systems design — deliberately giving up power to gain a property. RDDs surrender fine-grained writes and get near-free fault tolerance in exchange. It is the same instinct as Dynamo trading strong consistency for availability, or Firecracker trimming the device model to buy boot time.

Limits and criticism

  • Structurally wrong for fine-grained updates. The paper says so itself: RDDs do not suit asynchronous, record-at-a-time updates such as incrementally maintaining a web index (Google built Percolator for that) or implementing a storage system. This is an abstraction for bulk analytics, not a database.
  • Recovery is expensive with long lineage plus wide dependencies. Dozens of iterations each containing a shuffle mean one failure can trigger enormous recomputation — and deciding when to checkpoint automatically is left open in the paper, so in practice it stayed a human judgment call for years.
  • "N× faster than Hadoop" travelled further than it deserved. The speedup comes mainly from reusing one dataset and skipping serialization and disk round-trips; for single-pass ETL-shaped jobs the advantage is far smaller, and later work noted that the Hadoop side of such comparisons was often under-tuned.
  • Memory is a hard constraint. Once the working set no longer fits in cluster memory the advantage fades fast, and JVM object overhead plus GC pressure remained a chronic pain — which is what motivated Spark's later Tungsten work (off-heap memory and code generation).
  • The RDD interface is opaque to an optimizer. Operators carry arbitrary user functions, so the engine cannot see their semantics and cannot perform relational optimizations such as predicate pushdown or column pruning. Spark itself conceded this: from 2015 the DataFrame / Dataset API with the Catalyst optimizer became the recommended interface and the raw RDD API receded to a lower layer. In a sense RDD's success was being general enough that a higher abstraction could grow on top of it.

Takeaways

① In one line: an RDD is a read-only, partitioned in-memory dataset creatable only by coarse-grained deterministic transformations; fault tolerance comes from logging lineage and recomputing, not from replicating data.

② The pain: MapReduce hands off through HDFS at every stage, so iterative algorithms and interactive queries drown in disk round-trips — yet moving into memory hits the old wall that fine-grained-update systems can only survive failure by replication or update logging.

③ The trade: deliberately give up fine-grained writes, and "how this was computed" fits in tens of bytes — fault tolerance shifts from storing data to storing the recipe.

④ The premise: immutability plus deterministic transformations, which is what makes a recomputed partition byte-for-byte identical to the lost one.

⑤ Narrow dependencies (one to one) pipeline locally and recover cheaply; wide ones need a shuffle and can drag in every upstream partition — the scheduler cuts stages exactly at the wide ones.

⑥ Interface: lazy transformations, eager actions, so the engine optimizes over the whole DAG; persist() picks the storage level, and memory pressure evicts partitions LRU — an evicted partition is simply recomputed from lineage.

⑦ When lineage is too long, checkpoint to truncate it; immutability lets checkpoints be written asynchronously in the background with no stop-the-world snapshot.

⑧ Results: up to ~20× over Hadoop for iterative ML on 100 machines; 5–7 s interactive queries over 1 TB cached; a node failure slows only the iteration it hits; degradation under low memory is smooth.

⑨ Impact: the foundation of the whole Spark stack, and "recompute instead of replicate" as a standing route to distributed fault tolerance.

⑩ Limits: wrong for fine-grained updates; costly recovery on long lineage with wide dependencies and no automatic checkpointing; memory-hungry with JVM overhead; opaque to optimizers, later superseded as the recommended API by DataFrames and Catalyst.

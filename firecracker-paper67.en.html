Firecracker: Lightweight Virtualization for Serverless

Agache et al. · Amazon Web Services · NSDI 2020

中文 →

What did this paper do?

There is a kind of cloud service called "functions": you upload a small piece of code, never think about servers, and it runs only when someone calls it — billed by the millisecond. AWS Lambda is the biggest of them. In 2020 Amazon published the thing that actually runs your code underneath Lambda: Firecracker, a virtual machine shaved down to a skeleton. It lets one physical machine hold thousands of mutually distrusting customers' code at once, with each one booting in an eighth of a second.

First, a dilemma

Running a stranger's code on your own machine has always meant choosing between safe and fast.

A traditional virtual machine is safe: it hands each guest an entire fake computer, and whatever they do inside, they can't get out. The price is a boot that takes seconds and a few hundred megabytes of overhead — absurd for a function that runs for 20 milliseconds.

At the other end are containers: no fake computer, everyone shares one operating system and is merely shut into their own room. Light, and they start in milliseconds. But the walls of those rooms are that shared operating system, which keeps more than three hundred doors open to the outside — and those doors have been pried open before. Amazon was not willing to let mutually distrusting strangers share one operating system. The default assumption was: pick one.

The idea

Firecracker's idea is to interrogate that default: what exactly is slow about a virtual machine?

The answer: not the isolation, but the fact that it tries so hard to be a real computer. To be able to run any operating system at all, a general-purpose VM faithfully fakes an entire PC — power-on self test, floppy and optical drives, sound and graphics cards, USB ports, a whole expansion bus. On boot the guest has to walk that cabinet of fake hardware item by item, and that is where the seconds go. But a cloud function only needs to run a piece of code, not any antique PC. So shave the fake computer down to the few parts that are actually needed.

Shaved down to what?

The "computer" Firecracker hands each guest has exactly four things on it: a network card, a disk, one wire for printing logs, and a keyboard with a single key — and that key is power-off. No self test, no expansion bus, not even a boot screen: it drops the operating system straight into memory and starts at the first instruction.

Think of a capsule hotel that stops fitting every room with a kitchen, a garage and a garden, and leaves only a bed, a lock and the utilities — the guest only wanted a night's sleep anyway. Small rooms mean thousands per floor; quick turnaround means the next guest checks in as fast as the last one leaves.

Two more things came along with it. First, new building material: the program that hands out the rooms was rewritten in a language where security bugs are much harder to write, in about fifty thousand lines — where the veteran equivalent runs to over a million. Less code, fewer seams to pry at. Second, a second lock outside the door: if someone really did climb out of a room, what they land in is not the corridor but a small cage that was stripped of nearly every privilege in advance.

What it bought

Each of these "microVMs" costs under 5 MB of extra memory, takes about 125 milliseconds from creation to running customer code, and one machine can mint 150 of them per second. So a single physical machine can be packed tight with different customers' functions, none of them able to touch the others — safe and fast, no longer a choice of one. It was open-sourced in 2018, and both Lambda and Fargate run on it today.

One honest cost: this computer is deeply specialized — no graphics card, no expansion slots, so work that needs them simply cannot run here.

The one-line takeaway

Virtual machines are slow and heavy not because isolation is expensive, but because they pretend to be a real computer with everything on it. Shave the fake hardware down to a network card, a disk, a log wire and a power-off key, rewrite the manager in a safer language, and wrap a cage around it — the isolation is still virtual-machine grade, yet boot is an eighth of a second and the overhead is a few megabytes. That is how cloud functions got to be safe and cheap at the same time.

In one sentence

Firecracker is the minimal virtual machine monitor (VMM) AWS built for Lambda and Fargate: it throws away almost all of the hardware a general-purpose VMM emulates for the sake of generality, keeping only a virtio network device, a virtio block device, a serial port and a crippled keyboard controller whose sole job is to press "power off". Written in roughly 50,000 lines of Rust on top of Linux KVM, it gives each "microVM" a VMM memory overhead of under 5 MiB, about 125 ms from creation to user code, and up to 150 microVM creations per second per host — putting virtual-machine-grade isolation inside container-grade density and startup time for the first time.

Glossary

  • Virtual machine (VM) / virtual machine monitor (VMM, a.k.a. hypervisor): software that carves one real machine into several "fake computers", each running its own operating system; the program that builds and manages them is the VMM.
  • Guest / host: the system running inside the virtual machine is the guest; the system on the real machine underneath is the host.
  • KVM: the virtualization module inside the Linux kernel. It uses the CPU's own virtualization instructions to handle the hardest part of faking a computer — CPU and memory — so a VMM only has to emulate devices.
  • Container: no fake computer at all; several processes share the host's single kernel and are separated by namespaces (limiting what each can see) and cgroups (limiting what each can use). Light and fast, but the kernel is shared.
  • System call (syscall): the entry point a program uses to ask the kernel for a service (read a file, send a packet). Linux has more than three hundred of them; together they are the kernel's attack surface.
  • seccomp: a Linux filter that restricts a process to a named set of system calls and denies everything else.
  • virtio: a "paravirtualized" device interface designed for VMs — the guest knows it is virtualized, so instead of pretending to drive real hardware it exchanges data with the VMM through shared-memory ring queues, far faster than emulating a physical card instruction by instruction.
  • Serverless / FaaS: the user hands over a function and never manages servers; the platform bills per invocation and per millisecond of runtime. AWS Lambda is the archetype.
  • Cold start: a function has no ready environment right now, so one has to be created — the extra wait the caller pays for.
  • TCB (trusted computing base): the sum of code in a system that must be assumed not to have been compromised. Smaller is better.

Coordinates

The authors — Alexandru Agache, Marc Brooker and colleagues — are AWS engineers, and the paper appeared at NSDI 2020. Firecracker itself had been open source since late 2018; the code started as a fork of crosvm, Google's Rust VMM for Chrome OS, and the two diverged afterwards. It stands on KVM and virtio, the two pieces of infrastructure that made virtualization cheap, and it opened the way for the rust-vmm ecosystem and projects like Cloud Hypervisor that assemble a VMM out of Rust parts. Read it against the previous paper, the Berkeley View: that one argues about what serverless should be and what it lacks; this one shows how the brick underneath it was fired.

The problem

Early Lambda got its isolation from the EC2 instance boundary itself: one customer account's functions ran on virtual machines dedicated to that account, and different customers were separated by whole instances. Impeccable security, far too coarse a grain. A customer who only occasionally runs a 50 ms function still needs an instance standing by; instances boot in seconds, so capacity has to be reserved and kept warm. Low density means idle machines means cost — and cost is exactly what a per-millisecond billing model is selling against.

Raising density means packing different customers onto the same host, which forces the question: what serves as the isolation boundary? The paper lays the options out:

  • Containers: ideal density and startup, but the boundary is the entire Linux system call interface — three hundred-odd calls plus sprawling entry points like ioctl, /proc and /sys, which have produced escape vulnerabilities repeatedly. Stacking mutually distrusting tenants on one kernel was not an acceptable risk.
  • Language-level sandboxes (such as isolates in a JavaScript engine: several mutually invisible execution contexts inside one process): startup in milliseconds, but user code must be written in a particular language and runtime. Lambda has to support arbitrary languages, arbitrary binaries, even customers' own native extensions.
  • User-space kernels (intercept the guest's system calls and implement them in user space, as gVisor does): the attack surface really does shrink, but compatibility has to be rebuilt one syscall at a time and the interception itself costs performance.
  • Traditional virtual machines: exactly the isolation strength wanted, but off-the-shelf VMMs carry generality as dead weight — a million lines of C, a full PC device model, boots measured in seconds, tens to hundreds of megabytes resident per VM.

From that the paper states six hard requirements: isolation, overhead and density, performance close to bare metal, compatibility with arbitrary Linux binaries, fast switching (create and destroy in milliseconds), and soft allocation (oversubscription must be possible). Nothing available met all six, so they wrote their own.

The core ideas

Idea 1: what is slow is not virtualization, it is the device model

The pivotal judgement in the paper is that hardware virtualization itself is not slow. Since CPUs gained virtualization instructions and KVM moved that work into the kernel, the overhead of a guest executing instructions and touching memory has been small. The weight comes from the VMM's other job — faking an entire PC: BIOS self test, PCI bus enumeration, USB, floppy and optical drives, graphics, plug and play. The guest kernel probes that cabinet of fake hardware on boot, and most of those seconds go there — while the same emulation code is also the VMM's largest attack surface.

But a serverless guest is a Linux the platform itself supplies, running a customer's function. It never installs Windows, never needs a GPU, never hot-plugs USB. Once the compatibility requirement drops from "any operating system" to "any Linux binary", there is finally room to cut.

So Firecracker's device model retains four things: a virtio network device, a virtio block device, a serial port for logs, and a crippled keyboard controller whose only purpose is to let the host press "power off". No BIOS, no bootloader: Firecracker loads an uncompressed Linux kernel image directly into guest memory and jumps in according to the Linux boot protocol. The boot path is down to "load the kernel, find four devices".

The cost is explicit: the guest kernel has to be built for this stripped device set (virtio drivers on, most everything else off), and a customer who wants a GPU or PCI passthrough will not find one here. This is deliberate specialization, not an oversight.

Idea 2: treat the VMM itself as attack surface

If there is only one isolation boundary, that boundary has to be perfect. Firecracker assumes it is not, and stacks two.

The first is making the VMM small and sturdy: about 50,000 lines of Rust versus QEMU's million-plus lines of C — shrinking the attack surface along two axes at once, since Rust rules out buffer overflows and use-after-free at compile time, and those are precisely where VMM vulnerabilities come from. One microVM is one process, and each guest vCPU is a thread in that process, so a compromise or crash is contained to that one VM.

The second is the jailer: before Firecracker starts, it is locked in a cage — chroot for the filesystem root, namespaces for process and network views, cgroups for resources, dropped privileges so it does not run as root, and finally a seccomp allowlist permitting only the few dozen system calls a running microVM genuinely needs. The attack chain becomes: break the guest kernel, then break the KVM boundary, and even then land in a process that was stripped of privilege in advance.

The honest part: KVM and the host kernel remain in the TCB. This boundary is not zero-trust; it has merely been compressed onto a very narrow interface — the set of ioctls KVM exposes, far smaller than the full syscall surface.

Idea 3: knobs for oversubscription and noisy neighbours

Density is not only about fitting things in, it is about affording them. A function asks for 2 GB of memory and typically uses tens of megabytes. A microVM's memory comes from host pages allocated on demand: memory the guest never touches is never really handed over, so memory and CPU can be oversubscribed — what the paper calls soft allocation. That is the step that turns density into money.

The cost is neighbours competing for I/O. Firecracker therefore builds token-bucket rate limiters into the block and network devices (tokens drip into a bucket at a fixed rate and you wait when it is empty — capping the long-run average while still allowing short bursts), so the layer above can give each microVM a quota.

Its only external interface is a REST API over a Unix socket: configure the kernel, disk, network and vCPU count, then say "start". On each Lambda worker a component called the MicroManager drives that API, maintaining a pool of prepared microVM "slots" and assigning a slot to a function when a request arrives — a slot only ever serves one customer's one function, and is never reused across customers.

Key results

The paper's three headline numbers: under 5 MiB of VMM memory overhead per microVM, about 125 ms from creation to running user code, and up to 150 microVM creations per second per host. Those are the quantitative payoff for isolation, density and fast switching.

The evaluation puts Firecracker beside QEMU and gVisor on boot time, memory overhead and I/O throughput. Firecracker wins clearly on boot and memory — the firmware and device model it removed are exactly where QEMU spends time and bytes. On I/O the paper is candid: block and network throughput trailed QEMU's at the time; the trimmed virtio implementation gives up some performance, and the authors list it explicitly as known work remaining rather than papering over it.

For an industrial paper, though, the hardest evidence is not a benchmark: AWS Lambda runs entirely on Firecracker, and Fargate followed. Trillions of function invocations a day run on this thing — which says more about whether it holds up than any lab number.

Why it matters

  • It overturned an industry consensus. "Safe means slow, fast means sharing a kernel" was treated as a law of physics; Firecracker showed the slowness lives in the device model rather than in virtualization, so the dilemma was separable all along. Lightweight VMs became a standard infrastructure part afterwards.
  • It made the serverless economics real. Billing per millisecond only works if idle cost is low enough and switching is fast enough. Firecracker supplies that precondition — without it the pricing story does not close.
  • It seeded an ecosystem. After open-sourcing, Kata Containers could use it as a runtime and a wave of "VMs that start in a blink" products built on it directly; the rust-vmm community factored virtqueues, device models and the rest into reusable Rust crates that projects such as Cloud Hypervisor share. "Assemble your own VMM in Rust" became a realistic option.
  • It models a genre of paper: publishing a production system's real constraints, the alternatives that were rejected, and the potholes hit, is far more useful than a performance report alone.

Limitations and criticism

  • The feature set is deliberately lame: no PCI passthrough, no GPUs or accelerators, very few device types, so a whole class of workloads needing special hardware (much ML inference, for one) cannot run on it directly; at publication it targeted x86.
  • I/O performance trailed mature VMMs, as above and as the authors admit. Thinning the device model removes attack surface, but it also removes room for optimization.
  • Cold starts got cheaper, not abolished: 125 ms covers microVM creation to user code, while the bulk of a real cold start is often the customer's own runtime initializing (a JVM coming up, Python pulling in dependencies). The line of work that followed — snapshot and restore, saving the memory state of an already-booted microVM and reviving it in a blink — aims straight at that segment.
  • The TCB did not disappear: KVM and the host kernel still have to be trusted, and microarchitectural side channels (attacks that leak through structures shared inside the CPU) are not something a VM boundary stops; they need separate mitigations.
  • As an industrial paper it is not reproducible: Lambda's actual densities, oversubscription ratios and slot-reclamation policies are not published, leaving outside researchers with the paper's qualitative description.
  • It solves isolation and density, not serverless's structural problem: the complaint in the Berkeley View and in Hellerstein's contemporaneous paper — functions cannot talk to each other directly, so data must be shipped to the code — still stands. A better brick does not change the floor plan.

Takeaways

① In one line: shave a VM's device model down to a virtio NIC, a block device, a serial port and a power-off key, rewrite the VMM in 50k lines of Rust, and virtual-machine-grade isolation arrives at container-grade density and startup.

② The old pain: early Lambda gave each customer account its own instance — clean isolation, far too coarse; low density, boots in seconds, machines idling, all in direct conflict with per-millisecond billing.

③ Rejected alternatives: containers (boundary is 300+ syscalls, too wide), language sandboxes (locks in a language, compatibility fails), user-space kernels (compatibility and performance both cost), general-purpose VMMs (a million lines, second-scale boots, tens of MB resident).

④ The pivotal judgement: virtualization is not what is slow, the device model is. KVM already hands CPU and memory to hardware; the seconds go to BIOS self test and PCI/USB enumeration — and serverless only needs "any Linux binary", which is what makes the cutting possible.

⑤ The mechanism: no BIOS, load an uncompressed kernel and jump in; four devices only; one process per microVM with vCPUs as threads; a jailer outside (chroot + namespaces + cgroups + seccomp allowlist + non-root) as a second boundary.

⑥ Operational knobs: demand-paged memory enables oversubscription; token-bucket rate limiters on block and network devices handle noisy neighbours; the control plane is a REST API on a Unix socket, with a MicroManager owning slots that are never reused across customers.

⑦ Results: < 5 MiB overhead, ~125 ms to user code, 150 creations per second per host; it beats QEMU on boot and memory, trailed it on I/O at the time, and the paper says so; the hardest evidence is Lambda and Fargate in production.

⑧ Impact: it dismantled the false "safe vs fast" dilemma, made the serverless cost model real, and seeded the rust-vmm family of "build your own VMM in Rust" projects.

⑨ Limits: no GPU or PCI passthrough, an I/O performance debt, cold starts still dominated by customer runtimes (later addressed by snapshot/restore), KVM still in the TCB, side channels unstopped, operational parameters undisclosed — and no change to serverless's ship-data-to-code structure.
